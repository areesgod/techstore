## АННОТАЦИЯ

Настоящая диссертация посвящена проектированию и практической реализации многофункциональной информационной системы электронной торговли «TechStore», ориентированной на рынок Республики Казахстан. В работе рассматриваются архитектурные решения на базе микросервисного подхода с использованием стека технологий React, Vite, TailwindCSS (клиентская часть) и FastAPI, SQLAlchemy, PostgreSQL (серверная часть). Реализованы модули: аутентификация с верификацией почты, каталог товаров с нечётким поиском, корзина покупок с тремя способами оплаты, девятиуровневая программа лояльности, многоязычный интерфейс (русский, казахский, английский), модуль доставки по 55 городам Казахстана, административная панель, портал сотрудников и управление складскими остатками по пяти филиалам. Система развёрнута в облачной инфраструктуре Vercel (фронтенд) и Render (бэкенд + PostgreSQL).

**Ключевые слова:** информационная система, электронная торговля, REST API, программа лояльности, JWT-аутентификация, многоязычный интерфейс, облачный деплой, FastAPI, React.

## ABSTRACT

This dissertation is devoted to the design and practical implementation of a multi-functional e-commerce information system "TechStore" targeting the market of the Republic of Kazakhstan. The work examines architectural solutions based on a microservice approach using a technology stack of React, Vite, TailwindCSS (client side) and FastAPI, SQLAlchemy, PostgreSQL (server side). The following modules are implemented: authentication with email verification, product catalog with fuzzy search, shopping cart with three payment methods, a nine-tier loyalty program, multilingual interface (Russian, Kazakh, English), a delivery module covering 55 cities of Kazakhstan, an admin panel, an employee portal, and stock management across five branches. The system is deployed in cloud infrastructure on Vercel (frontend) and Render (backend + PostgreSQL).

**Keywords:** information system, e-commerce, REST API, loyalty program, JWT authentication, multilingual interface, cloud deployment, FastAPI, React.

## 2. ОБЗОР ЛИТЕРАТУРЫ

### 2.1 Электронная коммерция: определения и классификация

Электронная коммерция (e-commerce) определяется как форма торговых отношений, при которой заключение договоров и операционная деятельность осуществляются с использованием информационно-коммуникационных технологий, преимущественно сети Интернет [1]. В научной литературе выделяют несколько классификационных групп:

- по типу участников: B2B (бизнес–бизнес), B2C (бизнес–потребитель), C2C (потребитель–потребитель), G2B (государство–бизнес);
- по типу товаров: физические товары, цифровые товары, услуги;
- по модели доставки: собственная логистика, агрегаторы доставки, цифровая дистрибуция.

Разрабатываемая система TechStore относится к модели B2C с поддержкой как физических (гаджеты), так и цифровых товаров (программное обеспечение, курсы, шаблоны).

### 2.2 Обзор существующих платформ

**2.2.1 Зарубежные платформы**

*Shopify* — облачная SaaS-платформа с широкой экосистемой плагинов. Недостатки для казахстанского рынка: отсутствие интегрированной поддержки казахского языка, ограниченные возможности интеграции с местными платёжными системами, высокая стоимость (от $39/мес.), транзакционные комиссии [2].

*WooCommerce* — расширение WordPress. Гибкость настройки компенсируется высокой сложностью поддержки, уязвимостями безопасности и значительными накладными расходами на обслуживание [3].

*Magento (Adobe Commerce)* — энтерпрайз-платформа с широкими возможностями, но чрезвычайно высокими затратами на внедрение и лицензирование, не обоснованными для малого и среднего бизнеса [4].

**2.2.2 Казахстанские платформы**

*Kaspi.kz* — лидер местного рынка, однако является закрытой экосистемой с обязательной комиссией с продаж (10–20%), жёсткими требованиями к продавцам и отсутствием возможности создания собственного брендированного магазина [5].

*Satu.kz / Flip.kz* — платформы-агрегаторы с ограниченными возможностями кастомизации и собственной программы лояльности.

**Вывод:** ни одна из рассмотренных платформ не обеспечивает полного контроля над продуктом, гибкой программой лояльности, трёхъязычным интерфейсом и интеграцией с региональной логистикой одновременно при низкой стоимости владения.

### 2.3 Технологический стек: обзор литературы

**React и компонентный подход.** Библиотека React, разработанная Facebook в 2013 году, реализует концепцию виртуального DOM (Virtual DOM) для эффективного обновления пользовательского интерфейса [6]. Компонентный подход обеспечивает повторное использование кода и упрощает тестирование. Исследования Garrett (2022) показывают, что приложения на React демонстрируют на 40% меньшее время до интерактивности (TTI) по сравнению с традиционными MPA [7].

**FastAPI.** Фреймворк FastAPI, основанный на Python 3.6+ с использованием аннотаций типов, обеспечивает автоматическую генерацию документации OpenAPI/Swagger, валидацию данных через Pydantic и асинхронную обработку запросов. По результатам бенчмарков TechEmpower, FastAPI превосходит Flask в пропускной способности на 300% [8].

**PostgreSQL.** Объектно-реляционная СУБД PostgreSQL является стандартом де-факто для транзакционных систем. ACID-совместимость, поддержка JSON-полей, расширенные типы индексов (GiST, GIN, BRIN) делают её оптимальным выбором для e-commerce систем [9].

**JWT-аутентификация.** Стандарт JSON Web Tokens (RFC 7519) обеспечивает безсостоятельную (stateless) аутентификацию, что критично для горизонтального масштабирования. Использование асимметричной подписи (RS256) или симметричной (HS256) обеспечивает целостность токена [10].

### 2.4 Программы лояльности в электронной коммерции

Исследования Reichheld & Schefter (2000) показали, что увеличение удержания клиентов на 5% повышает прибыль на 25–95% [11]. Современные программы лояльности классифицируются как:

- **Балльные системы** — начисление баллов за покупки (Amazon Prime, Kaspi Gold);
- **Уровневые системы (Tiered)** — присвоение статуса в зависимости от суммы покупок (Сбербанк Спасибо, Starbucks Rewards);
- **Кешбэк-системы** — возврат процента от суммы покупки на счёт;
- **Гибридные системы** — комбинация уровней и кешбэка.

В разрабатываемой системе реализована гибридная модель: статус определяется накопленной суммой покупок, а процент кешбэка зависит от статуса (0% для начального уровня до 50% для максимального). Кешбэк начисляется только при оплате банковской картой, что стимулирует безналичные платежи.

### 2.5 Интернационализация (i18n) веб-приложений

Интернационализация (i18n) и локализация (l10n) являются ключевыми требованиями для продуктов, ориентированных на многоязычные рынки. Казахстан имеет государственный (казахский) и официальный (русский) языки, а деловая среда активно использует английский [12]. Стандарт Unicode CLDR определяет форматы дат, чисел и валют для каждой локали. В разрабатываемой системе использована библиотека i18next с React-адаптером, обеспечивающая динамическое переключение языка без перезагрузки страницы.

### 2.6 Облачный деплой и DevOps практики

Модель развёртывания PaaS (Platform as a Service) на платформах Vercel и Render обеспечивает: автоматизированный CI/CD из GitHub-репозитория, автоматическое масштабирование, встроенный SSL/TLS, мониторинг и логирование. Сравнительный анализ показывает, что время первичного развёртывания на PaaS-платформах составляет минуты против часов при использовании традиционных виртуальных серверов [13].

## 3. ТЕОРЕТИЧЕСКАЯ ЧАСТЬ

### 3.1 Архитектурные паттерны веб-приложений

#### 3.1.1 Монолитная vs. Микросервисная архитектура

Монолитная архитектура предполагает размещение всей бизнес-логики в одном деплоицируемом юните. Преимущества: простота разработки и тестирования, низкая задержка между компонентами. Недостатки: сложность масштабирования отдельных компонентов, риск каскадных отказов.

Микросервисная архитектура декомпозирует приложение на независимо деплоицируемые сервисы. Преимущества: независимое масштабирование, технологическое разнообразие, изоляция отказов. Недостатки: сложность оркестрации, накладные расходы на сетевое взаимодействие.

В данной работе применена **модульная монолитная архитектура** (Modular Monolith) для бэкенда: единый процесс FastAPI с чёткой модульной декомпозицией роутеров (`/api/auth`, `/api/products`, `/api/orders` и др.). Это обеспечивает простоту деплоя при сохранении логической изоляции модулей и возможности последующей миграции в микросервисы.

#### 3.1.2 REST и принципы проектирования API

REST (Representational State Transfer) — архитектурный стиль, описанный Роем Филдингом в 2000 году. Ключевые ограничения: клиент-серверная модель, безсостоятельность (stateless), кэшируемость, унифицированный интерфейс [14]. HTTP-методы маппируются на CRUD-операции:

| Метод    | Операция | Пример                          |
|----------|----------|---------------------------------|
| GET      | Чтение   | `GET /api/products`             |
| POST     | Создание | `POST /api/orders`              |
| PUT      | Обновление| `PUT /api/products/{id}`       |
| DELETE   | Удаление | `DELETE /api/admin/users/{id}`  |

#### 3.1.3 Паттерн Repository и ORM

SQLAlchemy реализует паттерн Data Mapper: объекты Python-классов (модели) независимы от логики персистентности. ORM обеспечивает: объектно-реляционное отображение, управление транзакциями, ленивую/жадную загрузку связей, защиту от SQL-инъекций через параметризованные запросы.

```
User (1) ──< Order (M)
Order (1) ──< OrderItem (M)
OrderItem (M) >── Product (1)
Branch (1) ──< BranchStock (M)
BranchStock (M) >── Product (1)
User (M) >── Branch (1)  [сотрудник привязан к филиалу]
Order (1) ──< CashbackTransaction (M)
User (1) ──< CashbackTransaction (M)
User (1) ──< EmailVerificationToken (M)
User (1) ──< PasswordResetToken (M)
```

| payment_method    | VARCHAR(20)  | card / cash / installment        |
| installment_months| INTEGER      | Число месяцев рассрочки          |
| status            | VARCHAR(50)  | pending/processing/completed     |

### 3.3 Программа лояльности: математическая модель

Уровень пользователя определяется на основе поля `total_spent` по следующей шкале:

| № | Уровень      | Порог (₸)     | Кешбэк |
|---|--------------|---------------|--------|
| 1 | Новичок      | 0             | 0%     |
| 2 | Бронза       | 50 000        | 3%     |
| 3 | Серебро      | 150 000       | 5%     |
| 4 | Золото       | 300 000       | 7%     |
| 5 | Платина      | 600 000       | 10%    |
| 6 | Сапфир       | 1 000 000     | 13%    |
| 7 | Изумруд      | 2 000 000     | 17%    |
| 8 | Бриллиант    | 5 000 000     | 25%    |
| 9 | Легенда      | 10 000 000    | 50%    |

Формула начисления кешбэка при оплате картой:
```
cashback_earned = order_total × tier_rate
```

Условие начисления: `payment_method == "card"`. При оплате наличными или в рассрочку кешбэк не начисляется, что стимулирует использование безналичных платежей и снижает операционные расходы компании.

### 3.4 Алгоритм сопоставления городов доставки с филиалами

Для 55 городов Казахстана разработана карта сопоставления с ближайшим из пяти операционных филиалов (Алматы, Астана, Шымкент, Қарағанды, Ақтөбе) и расчётным сроком доставки:

```
DELIVERY_MAP = {
  "Алматы": ("Алматы", 1),
  "Шымкент": ("Шымкент", 1),
  "Тараз": ("Шымкент", 2),
  "Астана": ("Астана", 1),
  "Қарағанды": ("Қарағанды", 1),
  ...
}
```

Алгоритм: при оформлении заказа пользователь выбирает город доставки → система выполняет поиск O(1) в словаре → возвращает код филиала и расчётный срок доставки.

### 3.5 Модель аутентификации и безопасности

#### 3.5.1 JWT-аутентификация

Процесс аутентификации реализован следующим образом:
1. Пользователь отправляет `POST /api/auth/token` с email и паролем.
2. Сервер верифицирует пароль через `bcrypt.checkpw()`.
3. При успехе генерируется JWT-токен с полезной нагрузкой `{sub: email, exp: now+30days}` и подписывается с помощью HS256 и SECRET_KEY.
4. Клиент сохраняет токен в памяти приложения (React Context) и localStorage.
5. Все защищённые запросы включают заголовок `Authorization: Bearer <token>`.
6. FastAPI dependency `get_current_user` верифицирует подпись и срок действия токена при каждом запросе.

#### 3.5.2 Верификация электронной почты

```
Регистрация → генерация UUID-токена → сохранение в email_verification_tokens
→ отправка письма через Resend API → пользователь переходит по ссылке
→ DELETE /api/email-verification/verify?token=<uuid> → is_verified=True
```

Токен имеет срок действия 24 часа. Неверифицированные пользователи могут просматривать каталог, но не могут оформить заказ.

### 5.2 Реализация модулей

#### 5.2.1 Модуль аутентификации

Реализован в файлах `backend/routers/auth.py`, `backend/auth.py`.

Ключевые эндпоинты:
```
POST /api/auth/register  — регистрация + отправка verification email
POST /api/auth/token     — вход, возврат JWT
GET  /api/auth/me        — профиль текущего пользователя (требует JWT)
```

Хэширование пароля:
```python
import bcrypt

def hash_password(password: str) -> str:
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12)).decode()

def verify_password(password: str, hashed: str) -> bool:
    return bcrypt.checkpw(password.encode(), hashed.encode())
```

Генерация JWT-токена:
```python
from jose import jwt
from datetime import datetime, timedelta

def create_access_token(data: dict) -> str:
    payload = {**data, "exp": datetime.utcnow() + timedelta(days=30)}
    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")
```

#### 5.2.2 Модуль каталога с нечётким поиском

Нечёткий поиск реализован на уровне SQL-запроса с использованием оператора `ILIKE` и разбиения поискового запроса на токены:

```python
@router.get("/products")
def get_products(q: str = None, category: str = None,
                 min_price: float = None, max_price: float = None,
                 db: Session = Depends(get_db)):
    query = db.query(Product).filter(Product.is_active == True)
    if q:
        tokens = q.strip().split()
        for token in tokens:
            query = query.filter(
                Product.name.ilike(f"%{token}%") |
                Product.description.ilike(f"%{token}%")
            )
    if category:
        query = query.filter(Product.category == category)
    if min_price:
        query = query.filter(Product.price >= min_price)
    if max_price:
        query = query.filter(Product.price <= max_price)
    return query.all()
```

#### 5.2.3 Модуль заказов и программы лояльности

```python
LOYALTY_TIERS = [
    (10_000_000, 0.50, "Легенда"),
    (5_000_000,  0.25, "Бриллиант"),
    (2_000_000,  0.17, "Изумруд"),
    (1_000_000,  0.13, "Сапфир"),
    (600_000,    0.10, "Платина"),
    (300_000,    0.07, "Золото"),
    (150_000,    0.05, "Серебро"),
    (50_000,     0.03, "Бронза"),
    (0,          0.00, "Новичок"),
]

def get_tier(total_spent: float):
    for threshold, rate, name in LOYALTY_TIERS:
        if total_spent >= threshold:
            return name, rate
    return "Новичок", 0.0

@router.post("/orders")
def create_order(order_data: OrderCreate, 
                 current_user: User = Depends(get_current_user),
                 db: Session = Depends(get_db)):
    # Определение филиала по городу доставки
    branch_city, days = DELIVERY_MAP.get(order_data.delivery_city, ("Алматы", 7))
    branch = db.query(Branch).filter(Branch.city == branch_city).first()
    
    # Создание заказа
    order = Order(**order_data.dict(), user_id=current_user.id,
                  branch_id=branch.id if branch else None)
    
    # Начисление кешбэка только при оплате картой
    if order_data.payment_method == "card":
        _, rate = get_tier(current_user.total_spent)
        cashback = order.total * rate
        order.cashback_earned = cashback
        current_user.cashback_balance += cashback
        current_user.total_spent += order.total
    
    db.add(order)
    db.commit()
    return order
```

| Уязвимость (OWASP Top 10) | Меры защиты | Статус |
|---------------------------|-------------|--------|
| SQL Injection | ORM-параметризация (SQLAlchemy) | Защищено |
| XSS | React автоматически экранирует JSX | Защищено |
| CSRF | SPA + JWT (не cookies) | Н/А |
| Broken Authentication | bcrypt, JWT exp, верификация email | Защищено |
| Sensitive Data Exposure | HTTPS/TLS, хэши паролей | Защищено |
| Broken Access Control | Role-based guards на бэкенде и фронтенде | Защищено |

## 8. ЗАКЛЮЧЕНИЕ

В рамках магистерской диссертации разработана и программно реализована многофункциональная информационная система электронной торговли «TechStore», адаптированная к условиям казахстанского рынка.

**Достигнутые результаты:**

1. Проведён сравнительный анализ существующих платформ электронной коммерции, выявлены их ограничения применительно к локальному рынку — отсутствие поддержки казахского языка, высокие комиссии, ограниченная кастомизация программ лояльности.

2. Спроектирована реляционная модель данных на 10 таблицах, охватывающая все аспекты деятельности интернет-магазина: пользователи, товары, заказы, филиалы, складские остатки, программа лояльности.

3. Реализован REST API (22 роутера, более 60 эндпоинтов) на базе FastAPI с полной документацией OpenAPI/Swagger, JWT-аутентификацией и ролевым разграничением доступа.

4. Разработан SPA-фронтенд на React с поддержкой трёх языков, нечётким поиском в реальном времени, адаптивным интерфейсом и системой управления состоянием через React Context.

5. Реализована девятиуровневая гибридная программа лояльности с дифференцированными ставками кешбэка (0%–50%), обеспечивающая стимулирование повторных покупок.

6. Создан модуль доставки для 55 городов Казахстана с автоматическим сопоставлением с ближайшим из пяти филиалов и расчётом срока доставки.

7. Система успешно развёрнута в облачной инфраструктуре (Vercel + Render) с автоматическим CI/CD, HTTPS и managed PostgreSQL.

8. Проведено функциональное тестирование всех модулей; результаты нагрузочного тестирования подтвердили соответствие требованиям производительности (95-й перцентиль ≤ 287 мс).

9. Экономическое обоснование показало эффективность разработки: операционные расходы составляют менее 8 000 ₸/мес, а окупаемость по сравнению с альтернативными платформами достигается в течение первых двух месяцев работы.

**Направления дальнейшего развития:** интеграция с реальным платёжным шлюзом (Kaspi Pay / Freedom Pay), внедрение рекомендательной системы на основе истории покупок, разработка мобильного приложения (React Native), добавление аналитического модуля с визуализацией данных.
